## What This Does

<!-- The path a submission takes, from arriving to the label a reader sees.
     Six or seven steps — this is the trace you wrote in Milestone 1. -->

Provenance Guard takes a piece of writing and tells the reader whether it was
probably written by a person, probably generated by AI, or too close to call.
It never sees who wrote it. All it has are two measurements of the text, and
the writer can always appeal.

### The path a submission takes

1. **The request arrives at `POST /submit`** (`app.py`). It brings `text` and
   `creator_id` as JSON. Nothing has been judged yet.
2. **The route checks the input.** Missing, empty, too-short or oversized text
   is refused with a 400 and an error code, and the refusal goes in the audit
   log. This step adds a guarantee that everything downstream gets text it can
   actually score.
3. **Signal one, `detector.model_signal(text)`, scores predictability.** GPT-2
   measures how predictable the text is (perplexity), squashed to 0–1, where
   higher means more AI-like. This step adds a reading of the *words*.
4. **Signal two, `stylometry.style_signal(text)`, scores shape.** It measures
   the text's shape: how much sentence length varies, how much vocabulary
   repeats, and how much and what kind of punctuation it uses. That gives a
   second 0–1 score, also higher = more AI-like. This step adds a reading of
   the *form*, independent of meaning.
5. **`scoring.combine_signals` combines the two scores into one.** This is
   where my rule for disagreement between the signals lives, and where I
   decide which way I'd rather be wrong.
6. **`scoring.score_to_label` turns the number into words.** The combined score
   becomes a guess (`human` / `unsure` / `ai`) and a sentence written for
   someone who has never heard of a threshold.
7. **The decision is logged and returned.** `audit.log_decision` writes all
   nine fields to `logs/audit.jsonl`, both signal scores included. The
   response hands the writer a `content_id`, which is the only thing they need
   to appeal through `POST /appeal`. An appeal moves the item to
   `under_review` without overwriting the original decision.

### Following a false positive through it

A real writer submits work they wrote themselves, and the service calls it AI.

**Who they are, most likely:** someone writing in a second language, or anyone
who writes plainly on purpose. They write short, ordinary sentences in common
words they're sure of.

**What score they get:**
- **Signal one:** GPT-2 finds common words in ordinary sentences easy to
  predict, so the model score comes out high, around 0.7–0.8. That's the same
  range as actual machine text.
- **Signal two:** sentences of similar length with a modest vocabulary and
  little punctuation beyond full stops. That's exactly the "even, narrow"
  shape it reads as AI, so the style score is likely 0.6 or above.
- **Combined:** both signals make the same mistake for the same reason, so
  combining them doesn't cancel it out. They agree with each other, and
  they're both wrong. With the starter's 0.5/0.5 weights and 0.65 AI
  threshold, that writer lands at about 0.7 and gets the high-confidence AI
  label.

**What the label says to them:** whatever I write for the high-confidence AI
label. If it reads like a verdict ("This was generated by AI"), it's an
accusation against someone who has the least room to argue back.

**What they can do about it:** `POST /appeal` with their `content_id` and a
reason. The item moves to `under_review`, the appeal sits in the log beside
the original decision, and nothing is re-scored automatically. A person has to
look. That only works if the response gave them the `content_id` and the label
told them an appeal exists.

**What this decides:** the AI threshold has to sit above where plain human
writing lands, even at the cost of letting some AI text through as `unsure`.
The AI label should describe what the measurement found, not what the writer
did, and it should point to the appeal. I'll check where a plainly written
human paragraph actually scores when I run the calibration inputs in
Milestone 4, and set thresholds from that, not from the defaults.

### The contract

**`POST /submit`**

Request (JSON):

| Field | Type | Required | Notes |
|---|---|---|---|
| `text` | string | yes | The writing to check. At least a couple of sentences; at most 20,000 characters. GPT-2 only reads the first ~300 words (400 tokens) anyway. |
| `creator_id` | string | yes | Whoever is submitting. Not used in scoring; used for the log, appeals, and unit 8's rate limit. |

Response `200`:

| Field | Type | Meaning |
|---|---|---|
| `content_id` | string (UUID) | This submission's id. The only thing you need to appeal. |
| `guess` | `"human"` \| `"unsure"` \| `"ai"` | Machine-readable verdict. |
| `confidence` | float 0–1 | How sure the service is of `guess`: the combined score for `ai`, 1 − combined score for `human`, and for `unsure`, how close the combined score is to the middle (1 − 2·\|score − 0.5\|). |
| `label` | string | The full sentence a reader sees. |
| `model_score` | float 0–1 | Signal one. Higher = more AI-like. |
| `style_score` | float 0–1 | Signal two. Higher = more AI-like. |
| `combined_score` | float 0–1 | Output of `combine_signals`. Higher = more AI-like. |
| `status` | `"decided"` | Becomes `under_review` after an appeal. |

Errors, always `{"error": "<code>", "message": "<sentence a person can act on>"}`:

| Status | `error` | When |
|---|---|---|
| 400 | `invalid_json` | Body isn't a JSON object. |
| 400 | `missing_text` / `missing_creator_id` | Field absent or not a string. |
| 400 | `empty_text` | Text is only whitespace. |
| 400 | `text_too_short` | Too few tokens for the model to score (`detector.perplexity` raises). |
| 413 | `text_too_long` | Over 20,000 characters. |
| 429 | `rate_limited` | Unit 8. |
| 503 | `detector_unavailable` | The model couldn't load. |

Every refusal is also written to the audit log with `audit.log_rejection`.

**`POST /appeal`**

Request (JSON):

| Field | Type | Required | Notes |
|---|---|---|---|
| `content_id` | string | yes | From the `/submit` response. |
| `reasoning` | string | yes | The writer's explanation, non-empty. |

The `creator_id` for the log entry is taken from the original decision, not
from the request, so nobody can file an appeal under someone else's name.

Response `200`:

| Field | Type | Meaning |
|---|---|---|
| `content_id` | string | Echoed back. |
| `status` | `"under_review"` | The new status. |
| `message` | string | Confirmation for the writer that a person will look at it. |

Errors: `400 missing_content_id` / `missing_reasoning`, `404 unknown_content_id`
(no decision with that id in the log), and `409 already_under_review` (a
second appeal on the same item).

## Signals and Scoring

<!-- For each signal: what property it measures, why that might differ between
     human and AI writing, and WHAT IT CAN'T SEE.

     The blind spot is not optional. If you can't name it you don't understand
     the signal yet — and unit 8's attack set is built out of blind spots. -->

### Signal one — the model signal

**What it measures:** How predictable the text is to GPT-2, running locally.
`detector.py` computes perplexity, which is the model's average surprise per
token over the first 400 tokens, then maps it onto 0–1 so that low perplexity
(predictable) scores high (AI-like). A perplexity of 45 scores 0.5.

**Why that might differ between human and AI writing:** a language model
writes by repeatedly choosing a likely next word, so its output is text a
model finds easy to predict. People make odder choices: a specific detail
instead of the typical one, an abrupt turn, a word nobody expected.

**What it can't see:** who wrote the text. Predictability isn't authorship.
What this signal really rewards is common words in short, ordinary sentences,
which is also how second-language writers, younger writers and anyone writing
plainly on purpose write. It scores them as machine-like. In the other
direction, ornate prose full of rare words reads as human, so AI text prompted
to "use unusual vocabulary" can slip past. It also only reads the first ~300
words.

### Signal two — the style signal

**What it measures:** The shape of the text, without reading a word of it. It
combines three measures: how much sentence length varies (standard deviation
over mean), how much of the vocabulary repeats (type-token ratio), and how much
punctuation there is and what kind (commas, semicolons, dashes). These go onto
a 0–1 score, with higher = more AI-like.

**Why that might differ between human and AI writing:** "most likely next
word", averaged over a whole passage, produces even, mid-length sentences, a
narrow band of vocabulary and tidy punctuation. Human writing is lumpier: a
three-word sentence next to a forty-word one, a stray dash, a repeated pet
word.

**What it can't see:** meaning. Anything that changes the shape without
changing the substance moves it. Typos raise vocabulary variety, splitting or
merging sentences raises length spread, and pasting in a quotation adds
punctuation. Each of those is a cheap, deliberate edit that makes AI text look
human. It's also unreliable on short text: one sentence has no spread at all,
and type-token ratio falls as text gets longer, so length alone can look like
a signal.

**Where the two blind spots overlap:** plain, even, simply worded human
writing looks AI-like to *both* signals. A second signal doesn't protect that
writer, because the two signals make the same mistake on the same text.

### The combining rule

<!-- Write the rule in words, then give the numbers. What happens when the two
     signals disagree? -->

**The rule:** a weighted average that leans on the model signal, because it
separated my test inputs better than the style signal did. If the two signals
are far apart, the result is pulled halfway toward 0.5. Two methods
disagreeing is uncertainty, so a big split should land in "unsure", not in a
confident verdict.

**The numbers:** `0.6 × model_score + 0.4 × style_score`. If
`|model_score − style_score| ≥ 0.5`, the score becomes `(score + 0.5) / 2`.
The weights and the 0.5 gap are in `config.py`.

**Where it lives:** `scoring.py::combine_signals`

<!-- ⚠️ The grader checks your code against that line. If your rule lives
     somewhere else, say where. -->

**How my style signal works** (`stylometry.py::style_signal`): three measures,
each flipped and scaled onto 0–1 (1 = AI-like), then averaged equally.
- **Sentence-length spread** (std ÷ mean of words per sentence): 0 → 1, and 0.6 or more → 0.
- **Type-token ratio:** 0.5 or less → 1, and 0.9 or more → 0.
- **Punctuation:** semicolons, colons, dashes and brackets per word. None → 1, and 0.03 or more → 0.

I left commas out of the punctuation count after my first version read the
clearly-AI text as human: AI lists are full of commas.

**Both signals on the four calibration inputs, plus plain human writing:**

| Input | model_score | style_score | combined | Label |
|---|---|---|---|---|
| Clearly AI | 0.903 | 0.509 | 0.746 | ai |
| Clearly human | 0.244 | 0.333 | 0.280 | human |
| Formal human | 0.629 | 0.233 | 0.470 | unsure |
| Lightly edited AI | 0.835 | 0.562 | 0.726 | ai |
| Plain human | 0.900 | 0.617 | 0.787 | **ai (false positive)** |

**A case where my two signals split, and what my rule does with it:** the
formal human text, a committee memo full of long, clause-heavy sentences. The
model signal leaned AI (0.63), because formal phrasing is predictable. The
style signal said human (0.23), because the sentence lengths vary and it uses
a colon. The weighted average puts it at 0.47, which is unsure. That's the
right outcome for a split: no accusation, and no false reassurance either.
The gap is 0.40, so the extra pull toward 0.5 didn't trigger. It's there for
bigger splits.

**What it can't fix:** plain human writing. Both signals read short, even
sentences and common words as AI, so they agree, and agreement is exactly
what the disagreement rule can't catch. This is the false positive from
Milestone 1, and it's why the AI label points to the appeal.

**Smaller findings:** at these lengths (40–60 words), type-token ratio comes
out 0.78–0.92 for everything, so it barely discriminates. Sentence-length
spread does most of the style signal's work.

## Label Variants

<!-- The exact text of all three labels, as a reader would see them, and the
     score range each covers.

     Write them for someone who has never heard the word "threshold". -->

| Label | Score range | The exact text a reader sees |
|---|---|---|
| high-confidence human | 0.00 – 0.35 | We think this was probably written by a person. |
| unsure | 0.35 – 0.70 | We can't tell whether this was written by a person or with AI help. This isn't a judgement about you or your work, and nothing has been flagged. |
| high-confidence AI | 0.70 – 1.00 | Our checks found patterns that often show up in AI-generated text. Automated checks can be wrong, especially on plain, simple writing. If you wrote this yourself, you can ask a person to review it. |

The text lives in `scoring.py` (`LABEL_HUMAN`, `LABEL_UNSURE`, `LABEL_AI`) and
the thresholds in `config.py`. I moved the AI threshold up from 0.65 to 0.70
so the AI label needs more evidence. All three labels are reachable: see the
table above.

**Why I worded the "unsure" one this way:**
<!-- It's the hardest of the three. It has to admit uncertainty without
     sounding like an accusation, because the person reading it may well have
     written every word themselves. -->
The person reading it probably wrote every word, so it says plainly that the
service is the one that doesn't know, not that the writer is under suspicion.
"Nothing has been flagged" answers the first thing they'll worry about. I
also wrote the AI label as what the checks *found*, not what the writer
*did*, and it admits the checks can be wrong and says how to appeal, because
plain writers land there.

## Rate Limiting

**My limits:** 5 per minute, 50 per day

**Why those numbers and not others:**
<!-- Think about two people: a real writer submitting their own work a few
     times an hour, and a script sending a thousand variations to map your
     thresholds. Your numbers have to be liveable for the first and hostile to
     the second. -->
A real writer submits a finished piece, maybe re-submits it after an edit or
two, and moves on. Five in one minute already covers someone fixing typos and
resubmitting quickly, and 50 a day is more than a heavy day of posting. A
script mapping my thresholds needs hundreds of near-identical variations to
find where the labels flip. At 50 a day that takes weeks per creator instead
of minutes, and every attempt is logged. The default of 10 a minute and 200 a
day would let a script collect 200 data points a day, which is enough to start
mapping the bands.

**What a caller counts as:** <!-- per address, or per creator_id? They fail
differently — one script can look like a thousand callers, and one household
can look like one. -->
Per `creator_id`, falling back to the caller's address when the request has no
usable `creator_id` (`app.py::rate_limit_key`). This is fair to people
sharing one network, like a household or a school, because each writer gets
their own allowance. The weakness is that `creator_id` is just a string the
caller sends, so a script can make up a new one for every request and never
hit the limit. That only works because nothing ties `creator_id` to a real
account. On a real site, the site would supply the id of the logged-in user.

## The Shape

**System:** Provenance Guard, the AI-text detection service from units 7–8.

**Shape:** A — Deploy and instrument. **Run path:** B — local with logs.

**What I'm adding:** the operational layer around the service as it already
works. Every request to `/submit` and `/appeal` will record how long it took,
including the requests it refuses (400, 413, 429), so the log answers "how
slow, and for what" without new code. The one-time model load at startup gets
timed separately, because the first request after a restart waits 10–20
seconds for GPT-2 while later ones take a second or two. `RUNNING.md` becomes
a single start command, tested from a fresh clone, with the environment it
needs (Python version, pinned packages, the 550 MB model). I'll measure what
one request costs in seconds of CPU time, averaged over ten runs. There's no
API bill, because the model runs locally. It runs locally rather than hosted
because GPT-2 alone needs more memory than the free tier's 512 MB.

**What I'll claim when it's done:** started from `RUNNING.md` alone, the
service records the duration of every request it receives, and I can say from
measurement what a cold request and a warm request each cost.

**Out of scope:**
- **Hosting it online.** The model doesn't fit the free tier, and getting it
  to fit would mean changing the detector.
- **Touching the detector, signals, weights, thresholds or labels.** Those
  belong to unit 8's improvement. Changing them here would make unit 8's
  before-and-after impossible to compare, and would make this unit's numbers
  about two changes instead of one.
- **New endpoints or a dashboard.** A `GET /metrics` route or a chart would be
  a second piece of work. The numbers come from reading `logs/audit.jsonl`.

**Size check:** the build is about 45–60 minutes. It means adding a timer and
a `duration_ms` field to the route and the log, timing the model load, and
writing `RUNNING.md`. Everything else this unit is measurement and write-up.

## Instrumentation

Every request to `/submit` and `/appeal` appends one JSON line to
`logs/audit.jsonl`. That includes requests the service refuses (400, 404, 409,
413, 429, 503) and requests that crash (500).

- **What came in:** `creator_id`, `endpoint`, `text_chars`, and for appeals `content_id`.
- **What came out:** `http_status`, the scores, `guess`, `label`, `status`, or `reason` for a refusal.
- **How long it took:** `duration_ms`, measured from the request arriving to the response being ready.
- **Whether it was a cold start:** `cold_start` is `true` on the request that waited for the model to load.

`GET /health` also reports `detector_load_ms`, the one-time load.

I log the text's length, not the text itself. The log should hold enough to
reconstruct what the service did, not a copy of people's writing.

**Code:**
- `app.py::_start_clock` starts the timer on every request. It's registered
  before the rate limiter, so a 429 gets timed too.
- `app.py::_elapsed_ms` reads the clock.
- `app.py::_crashed` logs any unexpected exception.
- `detector.py::_load` times the model load.

| One cold request (the first after a restart) | 57,363 ms |
| …of which loading the model | 48,558 ms |
| A refused request (400 / 429) | 2–4 ms |

**What that means:**
- **A warm submission costs about a third of a second** of one CPU.
- **Each restart costs about a minute** before the first answer, and almost
  all of that is loading GPT-2.
- **The cold number varies a lot from run to run.** The same load took
  23.3 s in one session and 91 s on the first run after a reboot. This
  measurement (48.6 s) ran while a `git clone` and a disk-size check were
  using the same disk.
- **Warm requests barely depend on length** in this range, because the
  detector reads at most 400 tokens of any text.
